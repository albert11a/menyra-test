# Second-pass gap audit for `apps/menyra-social/social-app.js`

Generated by static inspection on 2026-05-08 on branch `junivitefinal`.
Documentation only. No runtime code was changed.

Read this file together with `docs/architecture/social-app.js.md`. The first
architecture map remains broadly correct; this file records the gaps, sharper
risks, and verified areas found during a red-team pass against the real source.

## Audit Verdict

The first architecture document is a usable source of truth for the large
composition-root picture. The main missing risk is not a wrong high-level model,
but several under-specified edge contracts that are easy to break during a
kernel refactor:

- `index.html` is an active pre-app startup kernel, not just a loader.
- public bootstrap parses menu/focus payloads, but current route seed paths
  intentionally do not commit menu/focus items from that payload as final truth.
- `dataLoaded`, startup action locks, route replay, and listener cleanup are
  mutable root contracts outside the main `state` object.
- push/PWA/service-worker behavior writes Firestore device records and depends
  on exact build-token, SW scope, and message-handler wiring.
- the bridge layer hides a large dependency factory and a dynamic discovery/map
  import that must be treated as part of the current kernel.

## Verified From First-pass Doc

These first-pass sections were checked against source and are still correct in
the important shape:

- `social-app.js` is a browser ESM composition root with no exports; importing it
  starts the app.
- The single mutable `state` object is passed by reference through most runtime
  controllers.
- `render()` and `setState()` are not pure helpers. They own route sync,
  startup-snapshot side effects, render gating, fast DOM paths, and tab data
  loading.
- initial route parsing flows through `resolveInitialRouteState`,
  `pendingRouteState`, `applyPendingInitialRouteState`, and public direct entry
  seeding.
- QR public menu behavior depends on `src=qr`, `table`, `profileTopTab`, and
  `state.__webDirectEntry`.
- public menu truth is `state.menu.source === "public"` and is guarded by
  visible-target checks before commit.
- orders and media upload are intentionally deferred through proxy functions.
- auth/profile/CRM can read and write `users`, `restaurants`, `staffIndex`,
  `staffAdmins`, `superadmins`, and `leads`.
- route replay on `popstate` reparses the current URL and reopens profile,
  notification, post, and chat targets.

The first doc says the startup boundary is split across "three" source files but
lists four. The list is correct; the word "three" is a low-risk typo.

## Second-pass Findings

### 1. `index.html` pre-app startup behavior was under-specified

Status: confirmed by code.

Files:

- `apps/menyra-social/index.html`
- `apps/menyra-social/social-public-entry.js`
- `apps/menyra-social/social-public-bundled-entry.js`
- `apps/menyra-social/social-app.js`

What was missing or unclear:

- `index.html` sets `#app.dataset.startupSurface` before `social-app.js` loads.
- `index.html` canonicalizes public business routes with
  `window.history.replaceState` before the app starts. It removes aliases for
  `r`, `top`, `tab`, `uid`, `handle`, and `content`, but preserves canonical
  `src=qr` and `table`.
- bootstrap cache uses `BOOTSTRAP_CACHE_KEY = "mnyra.social.bootstrap.v1"` and
  `BOOTSTRAP_CACHE_TTL_MS = 5 * 60 * 1000`.
- startup snapshot restore checks both
  `mnyra.social.startup-snapshot.v2` and
  `mnyra.social.startup-snapshot.v1` with a 15 minute TTL.
- startup snapshot restore writes HTML into `#app`, sets
  `data-startup-snapshot="1"`, removes `aria-busy`, and sets
  `window.__MENYRA_SOCIAL_RESTORED_SNAPSHOT__ = true`.
- bootstrap route keys strip `sw-reset`, `cb`, `debug-build`, and `sw-off`.
- `shouldFetchBootstrap` intentionally skips map and public user routes, but
  fetches direct public web profile/menu and feed/home startup paths.
- bootstrap fetch is a CORS GET with `credentials: "omit"` and `cache: "no-store"`.
  Its URL can include `r`, `tab`, `top`, `src`, `table`, and `pathname`.
- viewport height syncing also runs on `document.visibilitychange`, not only
  resize/orientation/visual viewport events.

Why it matters:

This code can mutate the route, hydrate visible HTML, and seed bootstrap globals
before any module refactor code runs. Splitting the kernel around
`social-app.js` without preserving this HTML phase can cause route mismatches,
wrong startup surfaces, stale restored HTML, or duplicated bootstrap fetches.

What could break:

- `/:slug/menu?src=qr&table=7` could lose QR/table context during canonicalization.
- restored snapshots could be overwritten too early or never cleared.
- public profile startup could fetch bootstrap on routes where the app expects no
  bootstrap, or skip it on feed/profile routes.
- manual route tests could pass in raw module mode but fail in bundled mode.

Manual check later:

Open `/:slug`, `/:slug/menu`, `/user/:id`, `/map`, `/feed`,
`?sw-off=1`, and `?sw-reset=1` in a real browser. Confirm the final URL,
`data-startup-surface`, bootstrap presence, snapshot behavior, and first visible
surface match current behavior.

### 2. Bundled/raw entry selection has more globals than the first doc listed

Status: confirmed by code.

Files:

- `apps/menyra-social/index.html`
- `apps/menyra-social/social-public-entry.js`
- `apps/menyra-social/social-public-bundled-entry.js`
- generated bundle files under `apps/menyra-social/bundled/` were not audited
  as source of truth.

What was missing or unclear:

- `index.html` loads `/apps/menyra-social/bundled/manifest.json` with a 2500 ms
  timeout.
- raw entry is forced by `mnyra-raw-entry=1` or `raw-entry=1`.
- successful bundled dynamic import sets
  `window.__MENYRA_SOCIAL_BUNDLED_ENTRY_ACTIVE__ = true`.
- failed bundled import sets
  `window.__MENYRA_SOCIAL_BUNDLED_ENTRY_FALLBACK__ = true` and injects a
  raw `<script type="module">`.
- `social-public-bundled-entry.js` sets
  `globalThis.__MENYRA_SOCIAL_BUNDLED_ENTRY_PREPARED__ = true` before importing
  `./social-app.js`.

Why it matters:

Future extraction must work through all three entry modes: direct raw app,
public raw entry, and bundled public entry. A module path that works through
the raw `/apps/...` URL can still fail when imported relatively from the bundled
entry.

What could break:

- public website routes only fail in production bundled startup.
- degraded `app-entry` state is wrong, hiding entry failures.
- raw-entry debugging stops matching default startup behavior.

Manual check later:

Test default public startup and `?mnyra-raw-entry=1`. Confirm
`__MENYRA_SOCIAL_BUNDLED_ENTRY_ACTIVE__` or
`__MENYRA_SOCIAL_BUNDLED_ENTRY_FALLBACK__` has the expected value and the app
still reaches the same route/surface.

### 3. Startup bootstrap/auth sequencing is more tightly coupled than documented

Status: confirmed by code.

Files/functions:

- `apps/menyra-social/social-app.js`
  - `startAppStartupRuntimeCluster(...)`
  - `loadPersisted(...)`
  - `suspendRender()` / `resumeRender()`
- `apps/menyra-social/core/app-shell/app-startup-runtime-cluster.js`
  - `shouldDeferPersistedLoad(...)`
  - `schedulePostFirstPaintTask(...)`
- `apps/menyra-social/core/app-shell/app-startup-bootstrap.js`
  - `shouldDeferInlineBootstrapApply(...)`
  - `startAppStartupBootstrap(...)`
- `apps/menyra-social/core/app-shell/public-bootstrap-startup-utils.js`
  - `preparePublicBootstrapStartup(...)`
- `apps/menyra-social/core/auth/auth-session-startup-coordinator.js`
  - `createAuthSessionStartupCoordinator(...)`

What was missing or unclear:

- startup suspends render while the startup cluster begins, then replays a queued
  render after `resumeRender()`.
- persisted load can be split into `phase: "critical"` and a deferred full load
  after double `requestAnimationFrame` or timeout for profile/menu startup.
- `loadPersisted({ phase: "critical" })` intentionally skips
  `syncPersistedStories()` until the non-critical phase.
- inline public bootstrap can be deferred, except route-critical payloads with a
  restaurant id and `topTab`/`surface`/`contentTab` of `menu`, `profile`, or
  blank are forced immediate.
- auth startup binds the push open-target service-worker message handler before
  auth-driven route replay.
- guest tab ensure and public bootstrap fetch are scheduled differently for
  web-direct profile launches versus regular guest launches.

Why it matters:

This is not just "startup calls auth and bootstrap." It is a paint-order and
route-order contract. Moving persisted load, bootstrap application, or auth
listener binding can change first surface, stale data visibility, or protected
tab restoration.

What could break:

- public profile/menu cold start regresses to a blank or stale shell.
- cached auth profile hints display after live auth has already changed.
- stories/feed caches load too early during route-critical profile startup.
- push target URLs from service worker messages are ignored on startup.

Manual check later:

On slow network simulation or real mobile, refresh `/:slug`, `/:slug/menu`,
`/feed`, `/profile`, and a protected tab while signed in. Confirm the first
paint, route, auth state, and loaded stories match current behavior.

### 4. Public bootstrap normalizes menu/focus but route seed paths intentionally do not trust it

Status: confirmed by code. This is the most important semantic nuance found.

Files/functions:

- `apps/menyra-social/core/app-shell/public-bootstrap-runtime-controller.js`
  - `normalizeIncomingWebRoutePayload(...)`
  - `applyWebDirectRouteSeedFromBootstrap(...)`
  - `applyPublicBootstrapPayload(...)`
- `apps/menyra-social/core/profile/public-profile-direct-entry-controller.js`
  - `buildRoutePayloadSeed(...)`
  - `seedPendingDirectEntry(...)`
- `apps/menyra-social/core/profile/public-menu-surface-state-utils.js`
  - `resolveVisiblePublicMenuSurfaceState(...)`
- `apps/menyra-social/core/app-shell/session-data-runtime-controller.js`
  - `loadMenuForRestaurant(...)`
  - `loadFocusForRestaurant(...)`

What was missing or unclear:

- `normalizeIncomingWebRoutePayload(...)` can normalize
  `businessSnapshot.menu.items` and `businessSnapshot.focus.items`.
- current route seed paths later set:
  - `const routeMenuSeed = []`
  - `const routeFocusSeed = []`
  - `const routeMenuState = "unknown"`
  - `const routeFocusState = "unknown"`
  in both `applyWebDirectRouteSeedFromBootstrap(...)` and
  `seedPendingDirectEntry(...)`.
- menu/focus route payload output is then rebuilt from current
  `state.menu`/`state.focus` only when live public menu/focus truth already
  exists for the visible target.
- `resolveVisiblePublicMenuSurfaceState(...)` filters focus items so focus only
  renders when it matches loaded menu item ids or categories.

Why it matters:

A future refactor must not assume that bootstrap menu/focus arrays are allowed
to become visible truth just because they were present in the bootstrap payload.
The current behavior is stricter: public menu and focus remain live/cache loaded
truth and are only coordinated with the visible target.

What could break:

- stale menu/focus payload from bootstrap could render for the wrong restaurant.
- focus could show offers not backed by loaded menu items/categories.
- menu-first QR could appear "ready" before the actual public menu load settles.
- a refactor could accidentally turn `businessSnapshot.menu.items` into final
  menu state and bypass current safety guards.

Manual check later:

For a public business route with bootstrap payload, verify that menu and focus
visible state still comes from `restaurants/{rid}/public/menu`,
`restaurants/{rid}/public/offers`, `restaurants/{rid}/public/meta`, persistent
menu cache, or already committed public state, not from unverified route payload
arrays alone.

### 5. `dataLoaded` is a second mutable lifecycle state outside `state`

Status: confirmed by code.

Files/functions:

- `apps/menyra-social/social-app.js`
  - root `let dataLoaded = { feed, profile, restaurants, stories, following,
    notifications, leads, customers, staff, businessAccounts }`
- `apps/menyra-social/core/auth/tab-auth-load-utils.js`
  - `ensureTabDataCore(...)`
- `apps/menyra-social/core/app-shell/session-data-runtime-controller.js`
  - `bootstrapUser(...)`
  - `resetUserScopedState(...)`
- `apps/menyra-social/core/app-shell/session-tab-lifecycle-runtime-controller.js`
  - `preloadProfileData(...)`
  - `preloadMenuData(...)`

What was missing or unclear:

- `dataLoaded` is not part of `state`, but it controls one-shot loading for many
  tabs and domains.
- `ensureTabDataCore(...)` flips:
  - `feed` and `stories` on first feed load
  - `restaurants` on first non-landing restaurant truth prime
  - `profile` on profile load
  - `notifications`, `leads`, `customers`, `staff`, `businessAccounts` on their
    respective tabs
- `bootstrapUser(...)` may set `following` and preload restaurants/profile/menu
  based on auth-critical paths.
- `resetUserScopedState(...)` resets user-scoped flags such as `profile`,
  `following`, `notifications`, `leads`, `customers`, `staff`, and
  `businessAccounts`.

Why it matters:

Moving `ensureTabData`, auth bootstrap, or session data without `dataLoaded` can
cause duplicate reads/listeners, missing first loads, or stale role/admin data
after user switch.

What could break:

- feed or restaurant reads run repeatedly on every render/tab change.
- notifications/leads/customers/staff never load after a user switch.
- auth profile preloads are skipped because a flag stayed true from a previous
  user.

Manual check later:

After any session refactor, manually switch between guest, regular user, owner,
staff, and CEO if possible. Visit feed, profile, notifications, leads,
customers, staff, and business accounts and confirm each loads exactly once when
expected and refreshes after sign-out/sign-in.

### 6. Live listener cleanup has additional or dormant slots

Status: confirmed by code, with one uncertainty noted.

Files/functions:

- `apps/menyra-social/core/app-shell/session-tab-lifecycle-runtime-controller.js`
  - `startLiveListeners(...)`
  - `stopLiveListeners(...)`
- `apps/menyra-social/core/follow/follow-runtime-controller.js`
  - `startFollowingListener(...)`
  - `stopFollowingListener(...)`
- `apps/menyra-social/core/auth/tab-auth-load-utils.js`
  - `ensureTabDataCore(...)`
- `apps/menyra-social/core/app-shell/session-data-runtime-controller.js`
  - `startMenuMetaListener(...)`
  - `stopMenuMetaListener(...)`
- `apps/menyra-social/core/common/restaurant-identity-runtime-controller.js`
  - `ensureFeedRestaurantMetaListeners(...)`
  - `stopRestaurantMetaListeners(...)`

What was missing or unclear:

- first-pass live listener list omitted the following listener on
  `users/{uid}/following`.
- `startLiveListeners(...)` attaches current user profile, following, chat
  threads, notification DOM/update path, and push sync. It does not start orders;
  orders are tab-specific in `ensureTabDataCore(...)`.
- `stopLiveListeners(...)` stops chat threads, active chat messages, orders,
  notification listener, following listener, current user profile listener,
  profile view listener, feed/story unsubscribe slots, restaurant listener, and
  extra live listeners.
- `ensureTabDataCore(...)` always calls `stopRestaurantsListener()` at the start
  and stops chat/order/menu-meta/feed-story slots depending on tab.
- `session-tab-lifecycle-runtime-controller.js` owns `feedUnsub`,
  `storiesUnsub`, and `feedDeltaTimer`, but static search found no current
  producer assigning them beyond the injected setter slots. Treat these as
  dormant or reserved cleanup contracts unless later runtime evidence proves
  otherwise.
- `restaurant-identity-runtime-controller.ensureFeedRestaurantMetaListeners(...)`
  currently stops existing restaurant meta listeners and does not start new
  listeners. This means the older feed restaurant meta listener concept appears
  intentionally disabled in current source.

Why it matters:

A refactor that moves session lifecycle may accidentally drop cleanup calls that
are currently defensive but important for future or hidden paths. It may also
start orders or chat listeners in the wrong tab or for guests.

What could break:

- duplicate `users/{uid}/following` listeners.
- active chat messages keep listening after logout.
- orders listener stays active outside orders tab.
- a future feed/story listener producer has no cleanup path.

Manual check later:

After auth/session refactors, use browser Firestore/network logs if available.
Sign in, visit chat/orders/notifications/profile/feed, then sign out. Confirm
listeners stop and do not duplicate after signing in again.

### 7. Push/PWA/service-worker Firestore behavior was under-mapped

Status: confirmed by code.

Files/functions:

- `apps/menyra-social/core/router/deeplink-flow-utils.js`
  - `bindPushOpenTargetMessageHandler(...)`
- `apps/menyra-social/pwa.js`

What was missing or unclear:

- push registration writes device docs at
  `users/{uid}/devices/{deviceId}`.
- disabling push also writes to the same device doc.
- device id storage uses `pushDeviceIdKey()`, and token freshness metadata uses
  `pushTokenMetaKey(uid)`.
- push seen storage is capped by `PUSH_SEEN_NOTIFICATIONS_LIMIT = 120`.
- token sync freshness uses `PUSH_TOKEN_SYNC_INTERVAL_MS = 12 * 60 * 60 * 1000`.
- push uses `/shared/vendor/firebase/11.0.0/firebase-messaging.js`, the public
  VAPID key in `social-app.js`, `PUSH_SW_URL = /apps/menyra-social/sw.js?v=...`,

- `pwa.js` handles `sw-off=1` by unregistering app-scoped service workers and
  clearing caches whose keys start with `mnyra-social-cache-`.
- missing app version disables SW and clears social caches.
- update checks run every 30 minutes and on visible `visibilitychange`/`online`.
- service worker messages for push open targets are bound through
  `bindPushOpenTargetMessageHandler(...)`; the handler applies route state from
  target URLs and can open notification, post, chat, or profile targets.

Why it matters:

Push is tied to auth startup, notification runtime, PWA registration, and route
opening. A refactor that moves session startup or notification wiring can silently
break push routing or write stale device metadata.

What could break:

- `users/{uid}/devices/{deviceId}` stops updating, causing FCM delivery issues.
- `sw-off=1` no longer disables caches/service worker for debugging.
- push click target opens the wrong route or only works after app warm start.
- service worker update behavior forces reloads or interrupts deep links.

Manual check later:

After push/session refactors, verify push settings toggle, device doc write,
device disable write, `sw-off=1`, service-worker scope, and a push target URL
for notification/post/chat/profile.

### 11. Startup snapshot write/read contract is asymmetrical

Status: confirmed by code.

Files/functions:

- `apps/menyra-social/index.html`
  - `STARTUP_SNAPSHOT_KEYS`
  - `restoreStartupSnapshot(...)`
- `apps/menyra-social/social-app.js`
  - `STARTUP_SNAPSHOT_STORAGE_KEY`
  - `persistStartupSnapshot(...)`
  - `scheduleStartupSnapshotPersist(...)`

What was missing or unclear:

- HTML restores both v2 and v1 snapshot keys, but `social-app.js` writes only
  `mnyra.social.startup-snapshot.v2`.
- `social-app.js` removes only v2 when startup snapshots are disabled.
- snapshot write max is `STARTUP_SNAPSHOT_MAX_BYTES = 180000`.

reads/writes raw app HTML and depends on icon hydration and route key logic.

What could break:

- stale v1 snapshot restores while v2 is disabled/removed.
- HTML snapshot captures unhydrated icons or locked startup UI.
- public profile route shows a cached feed/profile shell for the wrong route key.

Manual check later:

When snapshot flag is enabled, load a route, refresh within 15 minutes, then
change route and refresh again. Confirm restored HTML only appears for the exact
route and is replaced by live render.
