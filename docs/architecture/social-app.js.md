# Architecture map for `apps/menyra-social/social-app.js`

Generated by static inspection on 2026-05-08 on branch `junivitefinal`.
This document is documentation only. It does not override `AGENTS.md`,
`docs/mnyra-launch-masterplan.md`, or `docs/mnyra-current-phase.md`.

## Purpose and scope

`apps/menyra-social/social-app.js` is the current browser ESM composition root
for the MNYRA social application. It is not only a render entry file. It owns the
single mutable app state object, creates most runtime controllers, wires Firebase
Auth and Firestore APIs into those controllers, parses and syncs routes, starts
the auth/session bootstrap, bridges public website bootstrap payloads, and exposes
several `window.__MENYRA_*` contracts used by HTML/bootstrap code and event
binders.

There are no exports from `social-app.js`. Loading the module is the startup
side effect.

Phase 1A update on branch `refactorapp`: `DEFAULT_PROFILE`,
`DEFAULT_SETTINGS`, and `DEFAULT_MENU_LAYOUT` now live in
`apps/menyra-social/core/app-shell/social-app-default-state-config.js` and are
imported back into `social-app.js` as named exports. `social-app.js` still owns
the `state` object identity, startup side effects, render/setState flow, route
sync, auth/session bootstrap, public menu/QR/cart/order behavior, and all
runtime controller wiring. Phase 1A moved only inert default config object
declarations; it did not move runtime behavior.

## Entry and startup picture

The startup boundary is split across three source files:

- `apps/menyra-social/index.html`
- `apps/menyra-social/social-public-entry.js`
- `apps/menyra-social/social-public-bundled-entry.js`
- `apps/menyra-social/social-app.js`

`index.html` is the first startup controller. Confirmed global contracts from
`index.html`:

- sets `window.__MENYRA_SOCIAL_SET_DEGRADED__`
- dispatches `CustomEvent("menyra-social-vendor-degraded")`
- defines `window.__MENYRA_SOCIAL_READ_PUBLIC_STARTUP_ROUTE__`
- sets `window.__MENYRA_SOCIAL_APP_VERSION__`
- sets `window.__MENYRA_SOCIAL_PUBLIC_WEBSITE_STARTUP__`
- sets bundle selection globals:
  - `__MENYRA_SOCIAL_BUNDLE_MANIFEST_PROMISE__`
  - `__MENYRA_SOCIAL_BUNDLE_ENTRY_KEY__`
  - `__MENYRA_SOCIAL_RAW_ENTRY_URL__`
  - `__MENYRA_SOCIAL_BUNDLE_MANIFEST_URL__`
  - `__MENYRA_SOCIAL_RESOLVE_BUNDLED_URL__`
  - `__MENYRA_SOCIAL_RESOLVE_BUNDLE_MANIFEST_ENTRY__`
- may set/restore public bootstrap:
  - `__MENYRA_SOCIAL_BOOTSTRAP_TIMEOUT_MS__`
  - `__MENYRA_SOCIAL_BOOTSTRAP_PAYLOAD__`
  - `__MENYRA_SOCIAL_BOOTSTRAP_PROMISE__`
  - `__MENYRA_SOCIAL_BOOTSTRAP_ENDPOINT__`
  - `CustomEvent("menyra-social-bootstrap")`
- handles early UI chrome/mobile behavior:
  - `window.history.scrollRestoration = "manual"`
  - `window.__MENYRA_SOCIAL_FORCE_UI_CHROME__`
  - resize/orientation/visualViewport CSS viewport syncing
  - pageshow scroll reset
- defers Lucide and PWA work; public website startup delays this more heavily.

Entry selection:

- For public website routes, `index.html` loads `social-public-entry.js` or the
  bundled public entry if the manifest succeeds.
- `social-public-entry.js` sets:
  - `globalThis.__MENYRA_SOCIAL_PUBLIC_ENTRY_ACTIVE__ = true`
  - `globalThis.__MENYRA_SOCIAL_ENTRY_MODE__ = "public"`
  - `globalThis.__MENYRA_SOCIAL_PUBLIC_ENTRY_VERSION__`
  - then imports `/apps/menyra-social/social-app.js?v=${APP_BUILD_TOKEN}`
- `social-public-bundled-entry.js` sets the same public-entry globals and also
  `globalThis.__MENYRA_SOCIAL_BUNDLED_ENTRY_PREPARED__ = true`, then imports
  `./social-app.js`.
- Non-public app starts load `social-app.js` directly.

Critical consequence: a future refactor cannot treat `social-app.js` as only an
app-route entry. It is loaded by public route entrypoints too, and it must preserve
public cold-start, QR, startup bootstrap, and guest behavior.

## Top-level side effects in `social-app.js`

Confirmed top-level work:

- reads `document.getElementById("app")` into `appEl`
- imports Firebase app/auth/firestore functions from shared vendor modules
- imports shared storage and image/runtime helpers
- imports many runtime clusters/controllers from `apps/menyra-social/core`
- initializes runtime error reporting with `createRuntimeErrorReporter`
- calculates perf mode and cache TTL/limits
- registers degraded/runtime diagnostics event listeners
- schedules media edge probes and perf warm markers
- creates the global mutable `state`
- creates controller clusters and stores their returned functions in local vars
- parses the initial URL through `resolveInitialRouteState`
- applies pending route state and direct public-profile entry hints
- wraps the render pipeline in `render()`
- binds `window.addEventListener("popstate", ...)` through
  `bindRoutePopstateReplay()`
- creates deferred orders and media upload proxies
- creates chat and session runtime clusters
- calls `startAppStartupRuntimeCluster(...)`
- calls `scheduleRuntimeDiagnosticsStartup()`

No build-time registration or export boundary exists. Importing the file starts
the app.

## Render and mutation contract

`render(...args)` is a wrapper around `renderShell(...args)` returned by
`createShellUiRuntimeCluster`. It does extra work on every render:

- calls `syncStartupSurfaceStatus()`
- computes `resolveStartupRenderGate(state)`
- calls `renderShell(...)`
- sets `window.__MENYRA_SOCIAL_APP_MOUNTED__ = true`
- clears `aria-busy`, `data-startup-shell`, and `data-startup-snapshot` on
  `#app`
- marks startup timeline when the first final surface is rendered
- calls `syncActiveTabRouteQuery()`
- schedules optional startup snapshot persistence

`setState(patch)` mutates state and owns the render scheduling behavior. It also:

- sanitizes tab changes for guest/auth state
- starts/finishes runtime budget traces for selected transitions
- uses fast-path DOM updates for drawer/notifications in limited cases
- queues `ensureTabData` when the active tab changes

Do not extract or bypass `render()` or `setState()` without preserving all of
these side effects.

## Public menu/focus/QR invariant

Current phase context says public menu + focus are in lockstep and the QR
behavior is invariant:

- QR links are created in the Menu Editor.
- A QR scan must land on the same profile page.
- The menu must be open immediately.
- Existing QR links must stay compatible.
- Cart/order logic must remain the same.

Confirmed code contracts supporting this:

- `resolveInitialRouteState` forces QR-like public business access to
  `pendingProfileTopTab = "menu"`.
- `pendingProfileTableNumber` is parsed from `table`, `tableNumber`, or `t`.
- `__webDirectEntry.menuAccessSource` and `.tableNumber` carry the QR/table
  context through public direct entry.
- `syncActiveTabRouteQuery()` preserves `src` and `table` when building
  canonical public business URLs.
- `core/profile/public-menu-surface-state-utils.js` treats route payloads as
  transport hints. Public menu truth remains `state.menu.source === "public"`.
- `core/profile/public-profile-surface-controller.js` resolves menu/focus
  visibility from live/current state, route payload, and `__webDirectEntry`.
- `core/app-shell/session-data-runtime-controller.js` guards menu/focus commits
  with visible target checks before applying public state.
- Public/QR guest menu load avoids the authenticated realtime meta listener
  path in relevant cases.

Do not split public menu/focus/QR startup before preserving this chain.

## Risky couplings

- `state` object identity is shared across almost every controller.
- `render()` is not a pure renderer; it syncs routes, startup mounted flags, and
  startup snapshots.
- `setState()` is not a trivial merge; it performs tab sanitation, render fast
  paths, budget traces, and data loading.
- Initial route parsing happens before full startup and before auth settles.
- `applyPendingInitialRouteState()` is coupled to direct public entry seeding.
- Public route cache globals can affect route parsing before Firestore reads.
- Public bootstrap can arrive through inline payload, promise, or custom event.
- Public menu/focus uses route payload only as seed/transport; Firestore public
  menu is still truth.
- QR/table parameters are carried through URL, pending route state,
  `__webDirectEntry`, profile surface, cart, and orders.
- `syncActiveTabRouteQuery()` runs after every render and can mutate browser
  history.
- Popstate replay can reopen profile/post/chat/notification targets.
- Deferred orders and media upload proxy functions are passed into event binders
  before the actual modules load.
- `window.__MENYRA_TOGGLE_MENU_ITEM_LIKE_FROM_CARD__` and
  `window.__MENYRA_REORDER_MENU_ITEM_FROM_ADMIN__` are called from event binders.
- Listener unsubscribe variables are split across root and controller modules.
- Auth restore state can preserve protected tabs for a cached returning user.
- Guest scope is session-scoped, but older guest storage keys are pruned/migrated
  in orders/session code.
- CRM flows can touch public visibility/meta and feed/story cleanup, not only
  lead/customer rows.

## Safe future refactor direction

Safest direction is incremental extraction around stable contracts, not moving
behavior first.

1. Keep `social-app.js` as the composition root initially.
2. Extract pure constants and dependency-factory builders only when they have no
   top-level browser/Firebase side effects.
3. Preserve the same imported module URLs, Firebase path strings, storage keys,
   state shape, function names, and controller dependency names.
4. Move one controller configuration at a time into small factory modules, while
   keeping `state`, `render`, `setState`, route sync, startup cluster call, and
   direct entry in `social-app.js`.
5. Add documentation/update maps after each extraction.
6. Only after route/auth/public-menu contracts are stable, consider splitting
   route startup, public profile startup, menu/focus, and auth/session into
   separate entry coordination modules.

Good first candidates for later extraction:

- static constants and storage key descriptions
- Firebase dependency object builders
- orders runtime config builder
- media upload config builder
- CRM dependency object builder
- chat dependency object builder
- pure route key helpers, if all browser history calls stay in the root

Poor first candidates:

- startup cluster call
- auth coordinator dependencies
- `render()` and `setState()`
- public route/direct-entry/menu/focus chain
- popstate replay
- menu/focus/QR/table behavior
- listener cleanup and startup order
