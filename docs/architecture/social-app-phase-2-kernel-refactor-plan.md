# social-app.js Kernel Refactor - Phase 2 Plan

Status: Phase 2B implemented on branch `refactorapp`.

Generated by static source inspection on 2026-05-08.

## Selected Target

Phase 2A selected Chat. Phase 2B kept that boundary and made the heavy Chat
runtime dynamic.

The implemented boundaries are:

- `apps/menyra-social/core/chat/chat-app-runtime-lazy-facade.js`
- `apps/menyra-social/core/chat/chat-app-runtime-facade.js`

`chat-app-runtime-lazy-facade.js` is the tiny startup-facing proxy imported by
`social-app.js`. It has no top-level imports from the heavy Chat facade,
`chat-runtime-cluster.js`, `chat-dom-utils.js`, listener, message, storage, or
render modules. It dynamically imports `./chat-app-runtime-facade.js` inside
`ensureChatRuntime()` only when Chat is actually needed. The real facade remains
the feature-owned wrapper around `core/chat/chat-runtime-cluster.js` and
`core/chat/chat-runtime-controller.js`.

## Why Chat Was Selected

Chat was the safest first runtime responsibility extraction because current
source shows it is not required for signed-out public business/menu cold load,
QR/table menu, cart, checkout, feed rendering, search, map discovery, or owner
menu/admin startup.

Source-verified current behavior:

- `ensureTabDataCore(...)` starts chat thread listeners for authenticated chat
  tab sessions and stops them for signed-out sessions.
- `startLiveListeners(...)` starts authenticated chat thread listeners together
  with profile/following/notification listeners.
- Chat route replay is isolated through `maybeOpenChatFromQuery(...)` and the
  bridge route API.
- Public menu, QR/table, cart, checkout, orders, and public bootstrap do not call
  the chat wrapper group.

## Why Safer Than Other Targets

CRM/Admin was not selected because source shows CRM reaches public business and
profile metadata through `ensureRestaurantPublicMeta(...)`,
`resolveRestaurantStatusFromLead(...)`, lead/customer/staff/business account
state, CEO scope, and business profile hydration. That is wider than a first
kernel extraction should be.

Discovery/map was not selected because it is already dynamically bridged through
`createDiscoveryRuntimeControllerAsync(...)`, while `/search`, `/map`, Leaflet,
marker/list behavior, and public profile navigation are launch-visible surfaces.

Notifications/push/follow were not selected as a separate first target because
push is tied to service-worker route messages and notifications startup. The
existing chat runtime controller currently owns some follow/notification action
methods, so Phase 2A preserves that existing source shape behind the chat facade
instead of reassigning domain ownership.

Public menu, QR, cart, and order were explicitly excluded because they are
launch-critical.

## Responsibility Moved Out Of `social-app.js`

Moved into `chat-app-runtime-facade.js`:

- chat runtime creation via `createChatRuntimeCluster(...)`
- chat constants:
  - `CHAT_MESSAGE_TTL_MS`
  - `CHAT_ATTACHMENT_INLINE_MAX_BYTES`
  - `CHAT_IMAGE_PREVIEW_COMPRESSION_STEPS`
  - `CHAT_MESSAGE_READ_LIMIT`
- chat DOM helper wrappers:
  - capture/restore chat input focus
  - scroll chat messages to bottom
  - autosize textarea wrapper
- chat thread index/storage wrapper methods
- chat message storage/sync wrapper methods
- chat listener wrapper methods
- chat send wrapper including the existing `chat_send` budget trace
- current chat-controller-owned follow/notification/post helper wrappers

## What Stayed In `social-app.js`

`social-app.js` still owns:

- state object identity
- render/setState
- route detection, route sync, pending route state, and popstate replay
- auth/session bootstrap and session runtime cluster creation
- public bootstrap/direct-entry behavior
- public business/menu/QR/table/cart/order behavior
- bridge shell runtime cluster creation
- small same-name adapter functions used by shell, bridge, session, and event
  binders
- follow, notification, and push runtime cluster creation in the existing
  session runtime cluster

## Initial-Load Impact

Phase 2B is intended to be a real initial-load reduction.

`social-app.js` no longer statically imports:

- `./core/chat/chat-app-runtime-facade.js`

It now statically imports only:

- `./core/chat/chat-app-runtime-lazy-facade.js`

The lazy proxy dynamically imports:

- `./chat-app-runtime-facade.js`

Expected network/HAR result: guest/public/feed/search/map/menu/QR cold loads
should not request heavy Chat runtime files. A Chat chunk/file should appear
only after `/chat`, a chat modal/thread open, a send/attachment action, or an
explicit chat notification target.

Synchronous callers remain synchronous through source-proven safe fallbacks:

- unread count returns `0` from empty state or the local cached count when
  available.
- missing thread, active thread, or blocked state returns `null`/`false`.
- list/index/message storage helpers keep deterministic localStorage behavior.
- DOM helpers keep no-op or safe focus/scroll/autosize behavior.
- render helpers return empty safe markup until the dynamic Chat runtime loads
  and schedules a render.

Async/action callers call `ensureChatRuntime()` and then delegate to the real
facade:

- send message
- add/read/build attachments
- start active message listener
- sync remote read state
- persist/sync remote message patches
- archive/delete thread
- follow request/accept/toggle helpers currently owned by the Chat controller

Notification handling is split so post/profile notification targets do not load
Chat. Only `chat_message` notification targets queue the dynamic Chat runtime.

Listener cleanup is safe if Chat never loaded: stop calls clear pending lazy
listener requests and no-op when the real facade was never imported. Auth/session
startup can call the proxy, but non-chat surfaces do not import or start the
heavy Chat listener unless the active surface is Chat or a real Chat action
requires it.
