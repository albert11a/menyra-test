# social-app.js Kernel Refactor - Phase 1 Plan

Generated by static inspection on 2026-05-08 on branch `junivitefinal`.
Documentation only. No runtime code was changed.

This plan is for a future implementation step. It does not authorize moving
startup, route, public menu, QR, auth, render, listener, push, cart, order, or
entry behavior in Phase 1.

## 1. Purpose

Phase 1 is a low-blast-radius preparation step for reducing
`apps/menyra-social/social-app.js`. The goal is to prove that small, inert
symbols can be extracted from the root module without changing startup order,
route behavior, state ownership, Firebase behavior, DOM output, or public guest
flows.

Phase 1 is not the kernel split. It is not a route split. It is not a public
menu or bootstrap refactor. It is not an auth refactor. It is not a render or
state refactor. It is not a performance project.

The recommended Phase 1 implementation style is:

- one extraction per task and commit
- only pure constants or pure key-builder helpers at first
- no behavior changes, no string value changes, no object shape changes
- no generated bundle edits
- documentation updates after each extraction
- manual testing by Albert after each extraction

## 3. Docs vs Source Verification

### What the docs said

The architecture docs describe `social-app.js` as the browser ESM composition
root. They correctly warn that importing the module starts the app, that it owns
the single mutable `state` object, and that it wires Firebase, Auth, Firestore,
routes, render, startup, public bootstrap, menu/focus/QR, orders, chat,
notifications, CRM, push, PWA, and bridge/controller dependencies.

The docs also recommend beginning a future split with pure constants and
dependency-factory boundaries, while avoiding route, startup, render, public
menu, QR, listener, and push behavior.

### What the source confirmed

Confirmed by code:

- `social-app.js` has no exports. Loading it is the startup side effect.
- `index.html` is a pre-app startup kernel. It sets app globals, restores
  startup snapshots, builds public bootstrap promises/payloads, canonicalizes
  public business routes, chooses raw vs bundled entry, defers Lucide, and
  schedules PWA loading.
- `social-public-entry.js` imports
  `/apps/menyra-social/social-app.js?v=${APP_BUILD_TOKEN}` after setting public
  entry globals.
- `social-public-bundled-entry.js` imports `./social-app.js` after setting
  public bundled-entry globals.
- `social-app.js` creates `state`, constructs controller clusters, parses the
  initial route, binds `popstate`, creates deferred orders/media proxies, creates
  chat/session runtime clusters, then calls `startAppStartupRuntimeCluster(...)`.
- `startAppStartupRuntimeCluster(...)` may split `loadPersisted(...)` into
  critical and deferred phases for profile/menu startup, then calls
  `startAppStartupBootstrap(...)`.
- `startAppStartupBootstrap(...)` binds public bootstrap payload handling and
  starts `createAuthSessionStartupCoordinator(...)`.
- `render()` calls `syncStartupSurfaceStatus()`, computes
  `resolveStartupRenderGate(state)`, delegates to `renderShell(...)`, clears
  startup attributes on `#app`, calls `syncActiveTabRouteQuery()`, and schedules
  startup snapshot persistence.
- `setState(...)` sanitizes tabs, starts budget traces for profile/menu opens,
  applies fast drawer/notification DOM paths, calls `render()`, and queues
  `ensureTabData(...)` when the active tab changes.
- Public route seed behavior still sets `routeMenuSeed = []`,
  `routeFocusSeed = []`, `routeMenuState = "unknown"`, and
  `routeFocusState = "unknown"` in all checked route seed paths:
  `public-bootstrap-runtime-controller.js`,
  `public-profile-direct-entry-controller.js`, and
  `profile-open-flow-utils.js`.
- `public-bootstrap-runtime-controller.js` does normalize menu/focus items from
  incoming route payloads, but the current seed paths do not commit those arrays
  as route truth. They only reuse existing live `state.menu`/`state.focus` when
  visible public truth is already present.
- Public menu/focus visible truth is still controlled by
  `session-data-runtime-controller.js` and
  `public-menu-surface-state-utils.js`, with visible-target guards.
- Orders and media upload are deferred by proxy functions. Orders also manage
  guest order storage and live order listener state.
- Push/PWA behavior is coupled to build tokens, service worker scope,
  Firebase Messaging dynamic import, notification runtime, and Firestore device
  registration writes.
- Feed stories still use `collectionGroup(db, "stories")` inside
  `story-feed-runtime-controller.js`.

### Mismatches or clarifications

Confirmed architecture-doc/source mismatch: none that changes the Phase 1
candidate ordering. The two architecture docs were broadly aligned with the
source on the key danger areas.

Important source/current-phase conflict: `docs/mnyra-current-phase.md` says Step
33 made direct public bootstrap menu/focus items become first visible public
truth. The source inspected in this pass still has empty route menu/focus seeds
and unknown route menu/focus truth in three route seed paths. Treat this as an
unresolved source-vs-current-phase conflict. Phase 1 must not touch this area.
Before any future public bootstrap/menu refactor, Albert or Codex must reconcile
the current phase note with the actual source and manual browser behavior.

Additional clarification: `FAST_LIMITS` and `SEARCH_LIMITS` look like constants
but are derived from `PERF_CONSTRAINED`, which is derived from `navigator` and
`safeStorage.getItem(PERF_WARM_KEY)`. They should not be moved together with
static cache key constants in the first cache extraction.

Additional clarification: `DEFAULT_NOTIFICATIONS` looks extractable, but it
uses `BRAND_UI.title`. Moving it would add either a new shared import or a
factory parameter. Do not include it in the first defaults extraction.

Additional clarification: `MENU_LAYOUT_COLORS` is static but directly affects
visible UI swatches/card classes. Leave it in `social-app.js` until there is a
specific menu-layout extraction task.

## 7. Rejected/Deferred Candidates

These may sound useful but are not safe for Phase 1.

- Startup cluster extraction:
  `startAppStartupRuntimeCluster(...)`, `startAppStartupBootstrap(...)`,
  `preparePublicBootstrapStartup(...)`, `createAuthSessionStartupCoordinator(...)`.
  Rejected because startup order controls render suspension, auth restore, public
  bootstrap, push target binding, and first visible route.

- Route/direct-entry extraction:
  initial `resolveInitialRouteState(...)`, `pendingRouteState`,
  `applyPendingInitialRouteState(...)`,
  `publicProfileDirectEntryController`, `state.__webDirectEntry`,
  `profile-open-flow-utils.js` route seed behavior,
  `bindBrowserPopstateRouteSync()`, and `replayRouteFromWindowLocation()`.
  Rejected because public profile/menu/QR/back-forward behavior depends on exact
  ordering and mutable root state.

- Public bootstrap/menu/focus extraction:
  `applyWebDirectRouteSeedFromBootstrap(...)`, `state.__publicRouteBootstrap`,
  `loadMenuForRestaurant(...)`, `loadFocusForRestaurant(...)`,
  `resolveVisiblePublicMenuSurfaceState(...)`, public menu truth/focus truth,
  and QR/table propagation. Rejected because source and current phase docs
  conflict on route bootstrap menu/focus semantics.

- Render/state extraction:
  `render()`, `setState()`, `syncActiveTabRouteQuery()`, startup snapshot
  persistence, startup action locks, and fast DOM paths. Rejected because these
  are behaviorful kernel functions.

- Entry and HTML extraction:
  `index.html`, `social-public-entry.js`, `social-public-bundled-entry.js`, and
  generated bundled output. Rejected because entry selection and pre-app
  bootstrap behavior must stay stable.

- Push/PWA/session config extraction:
  `FIREBASE_MESSAGING_MODULE_URL`, `PUSH_*`, `FCM_WEB_PUSH_VAPID_KEY`,
  `pwa.js`, push device registration, and service-worker scope/update behavior.

- Orders runtime config extraction:
  `createOrdersRuntimeControllerConfig(...)` and
  `createDeferredOrdersRuntimeController(...)`. Rejected for early Phase 1

- Media upload runtime config extraction:
  `createMediaUploadRuntimeControllerConfig(...)`,
